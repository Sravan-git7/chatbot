## Local Rust is not a blanket exemption

The existing same-version inert probe in `release/closure_v1/chroma_inert_probe.{py,json}` demonstrates registered-provider construction during config deserialization and through a Rust persistent collection's `.configuration` property. It uses a no-network/no-model hook, not remote code. `get_collection`, explicit-vector `get`, and explicit-vector query did not construct the hook in that fixture. That is a narrow data-flow observation, not package clearance or production penetration testing.

Current application AST inventory finds **no `HttpClient`/`AsyncHttpClient` constructor or `.configuration` property access in `scripts/*.py`**. `rag_api` exposes chat/health/static routes, not collection management. The shipped factory uses `OwnedCardBackend`/`OwnedPageRetriever`, fixed local paths, `get_collection`, actual stored-vector reads and explicit query embeddings. Raw imported legacy `rag_core` also has a separate local `chroma_db` reader; import is not a call to that reader. Builders, diagnostics, repair and legacy utilities have their own local SDK constructors and must not be exposed as web endpoints. This inventory is not a complete dynamic call graph, native SBOM or proof of the user's deployment topology. Poisoned local stores/models, dynamic configuration or a separately running Chroma server remain material threats.

## Concrete containment plan while no supported patch exists

These are **required proposed controls**, not assertions that infrastructure has applied them:

1. **Operations / no exposure:** inventory service-manager/container commands, backend/provider settings, every listener/interface and ingress path. Run no Chroma HTTP service; do not publish its ports or proxy its API. Independently allowlist only the application's approved chat/health/static methods/routes. Deny **all versions** of tenant/database/collection management and data CRUD routes, all verbs, encoded/trailing-slash variants and alternate ingress paths. Do not rely on Chroma auth for the pre-auth create path. From both untrusted and lower-privileged test networks, record deny responses and confirm no model/config constructor side effect. Local absence of a listener here is not target proof.
2. **Security + data owner / code provenance:** service account has no administrative updater or store/model writer authority. Approve immutable, hashed local model/tokenizer/config/store artifacts; ingestion/repair runs separately with explicit review and cold backups. Deny unapproved repositories, `trust_remote_code`, remote provider configuration and arbitrary filesystem model paths at every accepted configuration boundary. Do not inspect untrusted `.configuration` through the Python SDK as a supposedly passive validation step. Store metadata/dimension checks alone do not authenticate embedding-function configuration.
3. **Infrastructure / blast radius:** separate OS users/processes and stores per principal/security domain; no shared multi-tenant Chroma server/SimpleRBAC trust boundary. Apply read-only mounts/ACLs where the SDK's tested access pattern permits them, no host sockets, minimal secrets/privileges and outbound network deny by default. Writable runtime directories must be separate from approved immutable artifacts. A sandbox cannot stop malicious already-local model code; provenance and privileges both matter. Validate that these restrictions do not break normal Chroma operation before approval.
4. **Identity owner / independent authorization:** use authenticated ingress with principal-bound authorization, document ACLs and TLS; test principal A against B for collection discovery/read/query/add/update/upsert/delete/count and management, across v1/v2 and any SDK path. No cross-tenant data, mutation, count leakage or model-config privilege escalation is acceptable. An application token and conversation ID are not these controls.
5. **Security owner / patch watch:** follow all four advisories and PR 7602; pin reviewed release/wheel/source hashes when a supported patch appears. Then perform package/native graph review, actual Windows lifecycle, backend integration, frozen strict quality, model behavior, API/browser/auth isolation and load/cancellation/drain/rollback compatibility **before** adoption. No untested upgrade/downgrade or ad-hoc local patch is authorized.
6. **Release authority / decision:** attach enforcement configuration, network/process evidence, artifact provenance, negative tests and residual-risk analysis to a named security/infrastructure approval. If material reachable critical/high auth/isolation risk remains, do **not** activate. No acceptance/waiver is recorded here; even an approved security exception would not close missing mandatory quality/Windows/runtime gates.

**Next human action:** provide the actual private target's topology/provider configuration and authorized security/operations owners, plus approval for an isolated containment/isolation rehearsal. No production activation, migration, store replacement or public deployment is authorized by this plan.
