# Phase 6 - repository audit (read-only)

Scope: the nine tracked files that `git status` reports as modified against `main` (commit `d85c31e`, "Baseline SAP RAG pipeline and retrieval evaluation"), judged from their actual diffs. Nothing was reverted, cleaned up, committed or rebuilt. All findings are from reading files; the production pipeline could not be executed here (there is no `chroma_db/`, and no Ollama).

## 0. How the evidence was gathered

* `git status`, `git diff` and `git show HEAD:<path>` for each file. Unified diffs were read in full for the small files. The rewritten files (`rag_chat.py`, `retrieve.py`, `evaluate_retrieval.py`, `audit_corpus.py`) were compared side by side with `HEAD`.
* `data/retrieval_results.json` was compared with its `HEAD` version field by field.
* Usage was traced with `grep` (imports, tests, README references).
* **Who made the modifications cannot be determined from git.** The checkout is a fresh clone (`reflog`: clone, then checkout of the working branch) with no local commits and no stash. Every file in the working tree has the same restore timestamp, so modification times carry no information. The previous phase's statement that these changes predate Phase 5 is consistent with what was found, but it is not independently provable. The audit therefore does not assume they are mine or the user's.
* Whitespace check: the diffs are real content changes, not line-ending noise (none of the nine `HEAD` or working copies contains a CR character, and `git diff -w` leaves almost the same size).

## 3. Answers to the six audit questions

1. **What each modification changes:** see the table. In short, three groups:
   * a *refactor of the legacy chatbot* into `rag_core.py` (`rag_chat`, `retrieve`, `evaluate_retrieval`, `create_embeddings`), plus path anchoring (`chunk_pages`, `clean_sap_pages`);
   * a *file reuse* (`audit_corpus.py`, Phase 0 PDF audit replaced by the page-corpus audit);
   * *housekeeping and generated output* (`.gitignore`, `data/retrieval_results.json`).
2. **Related to the existing SAP RAG application?** Seven of nine are (the refactor group, path anchoring, `retrieval_results.json`). `audit_corpus.py` belongs to the 29-topic page-ingestion tool chain, not to the running chatbot. `.gitignore` serves both.
3. **Conflict with the M2C card retrieval work?** No functional conflict found. The card scripts do not import any modified module. Isolation is enforced by tests: `tests/test_sap_resolver.py::IsolationTests` asserts that the runtime modules do not reference `sap_resolver`, `tests/test_phase5.py` asserts the Phase 5 scripts do not import `rag_core`, `rag_chat`, `retrieve`, `evaluate_retrieval` or `create_embeddings`, and `build_card_collection.py` refuses the name `sap_docs` and any directory named `chroma_db`. Two real risks remain: the **`audit_corpus.py` name collision** and the **untracked `rag_core.py` dependency**.
4. **Safe to preserve?** Yes for all nine. None is destructive on its own, and all are recoverable from `HEAD` where they replace old content. Reverting any of them now would break tests (`audit_corpus.py`) or the documented application (`rag_core` consumers).
5. **Accidental / generated / experimental / intentional?**
   * intentional: `rag_chat.py`, `retrieve.py`, `evaluate_retrieval.py`, `create_embeddings.py`, `chunk_pages.py`, `clean_sap_pages.py`, `audit_corpus.py` (each has a docstring or README entry explaining it);
   * generated: `data/retrieval_results.json`;
   * housekeeping: `.gitignore` (the removed lines look like an earlier accidental paste).
   * Nothing looks experimental or throw-away.
6. **Affects the current RAG pipeline?** Yes, in three ways, all of which matter when integrating:
   * the default retrieval strategy is `improved` rather than the old `rag_chat.py` behaviour (`current`): one chunk per page content, deterministic tie-break;
   * generation is deterministic (`temperature 0`, `seed 42`), so answers may differ from those produced by `HEAD`;
   * startup no longer loads the model and database at import time (lazy singletons).
   The numbers that define the legacy retrieval baseline did not change (88/96/100% loose; the `current` and `improved` results are identical on hits).

## 4. Facts that matter for the next phases

* `chroma_db/` (collection `sap_docs`) is gitignored and is **not present** in this checkout, so the production pipeline has not been run or re-verified here. The legacy source data is present and identical to `HEAD` (`sap_pages/` 81 files, `cleaned_pages.json`, `chunks.json` 310 chunks).
* `data/vector_store/` (collection `sap_m2c_card_v1`) is also gitignored and **absent** in this checkout. It is required by seven existing tests (they skip without it), and it has to be rebuilt by `scripts/build_card_collection.py` before any integration work. Phase 6 did not rebuild it, as instructed.
* Opening a Chroma store in place changes its files (observed in Phase 5: the byte-level hash of the store changes after the Phase 4 tests open it). Store identity must therefore be checked by content (vectors, ids, documents), not by file hashes.
* No tests cover `rag_core.py` or the legacy scripts. `scripts/test_retrieval.py` and `scripts/test_search.py` are ad-hoc scripts that connect to `chroma_db` at import time, which is why bare `pytest` fails at collection and `pytest tests` is used.
* `fetch_sap_pages.py` (tracked, unmodified) is the only legacy code that touches the network. It is hard-wired to deliverable `40374631`, build `1779`, and uses working-directory-relative paths.
