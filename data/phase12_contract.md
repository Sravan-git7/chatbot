Scope source: the user's Phase 12 instruction (parts A-K). This is **not** an optimisation round. No router, retrieval, threshold or generator change is evaluated or adopted in this phase unless it is *both* (a) unblocked by the real corpus / real LLM path having been exercised and (b) pre-declared below. Architecture is unchanged: UI -> FastAPI -> `rag_service` -> routing -> identity -> page retrieval -> evidence -> generator -> citation. No second RAG implementation.

Starting state: Phase 11 + 11.1 committed as `f5cddbc` on `arena/01a0ed60-chatbot` (PR #1 open, not merged). Verified before this contract: Python 908 passed, vitest 52, tsc clean, browser E2E 28/28, product E2E 11/16, `git diff --check` clean, protected hashes unchanged.

## C1 - Corpus acquisition

Questions answered per card (all 29), recorded in `data/phase12/corpus_status.json` (generated by `scripts/phase12_corpus_status.py` from the existing Phase 7C identity file, Phase 8 page manifest and the Phase 9 / Phase 12 fetch logs; nothing is hand-edited):
verified identity status (Phase 7C vocabulary preserved: `resolved_local_page`, `identified_not_local`, `corrected_identity`, `card_identity_only`, `conflicting_identity`; `unresolved` = any card with no effective guide/page), official SAP Help URL as stored on the card (never rewritten), effective guide/page id, local page present, chunk count in the page store, answerable content (a page with >= 1 chunk), request that would be needed, latest fetch result.

Rules:
1. Retrieval uses only `scripts/page_fetch.py` (official `help.sap.com/http.svc/pagecontent`, recorded numeric deliverable ids only, robots read first, 3-failure circuit breaker). No other host, no third-party copy, no guessed id/URL, no URL rewriting.
2. The Phase 12 attempt is logged to `data/phase12/fetch_attempt_log.json` (the Phase 8/9 logs are not touched).
3. If help.sap.com is unreachable the corpus part is **BLOCKED** and is never reported complete. The 18 `identified_not_local` cards that have recorded ids stay `not_ingested_no_local_content`; the 3 `card_identity_only` cards and the conflicting card M2C-18 have no verifiable page id and are not fetchable.
4. For the blocked part an exact import procedure is produced (`data/phase12/import_manifest.json`, `data/phase12/IMPORT_INSTRUCTIONS.md`, validator `scripts/phase12_import_pages.py`): the user (or any machine with access and a decision about the robots.txt `Disallow: /`) saves the listed `pagecontent` responses; the validator accepts a file only if its `currentPage.loio` and `deliverable.loio` equal the plan entry (same checks as `page_fetch.check_response`). It never fetches. Importing changes the corpus, so tests that pin the 7-page corpus will (correctly) fail afterwards and must be reviewed deliberately, not auto-updated.
5. Phase 7 identity evidence and manifests are read-only.

## C2 - Real Ollama execution

`scripts/phase12_ollama_check.py` records (to `data/phase12/ollama_environment.json`): executable on PATH, python `ollama` package, server on 127.0.0.1:11434 (`/api/tags`, `/api/version`), presence of the configured model `llama3.2:3b` (from `rag_core.LLM_MODEL_NAME`, options `{temperature 0, seed 42}`), version, a 1-token generation round trip if (and only if) all earlier checks pass. Host resources are recorded (CPU, RAM) because they decide whether a 3B model is usable.
Rules: no model/binary download without explicit permission; no stub counted as LLM evaluation; the evaluator's `ollama` configurations run **only** when the check says ready and otherwise record `BLOCKED` with the reason (never an extractive fallback). If blocked, the exact machine-side commands are written to `data/phase12/IMPORT_INSTRUCTIONS.md` and the evaluation command is left ready.

## D - Fresh evaluation set (`data/evaluation/phase12_queries.json`)

AI-authored (disclosed in the file; not blind, not human-labelled; the author had read all 7 page texts and the Phase 11.1 results), written and frozen (sha256 in `phase12_freeze.json`) by `scripts/build_phase12_queries.py` **before any Phase 12 retrieval or evaluation ran**. The builder validates: gold evidence quotes lie inside one chunk of the gold page; absent-detail terms do not occur in the page text; no overlap (exact or token Jaccard >= 0.8) with Phase 8/9/10/11.1/E2E questions or inside the set; it refuses to re-run. Categories (field `category`): direct_factual, paraphrased, terminology, code_transaction, numeric_detail, absent_detail, out_of_domain, sibling_topic, ambiguous, corrected_identity, review_conflict. Record `type` follows the earlier schema (answerable, absent_detail, not_ingested, unresolved_identity, out_of_domain) plus `ambiguous` (acceptable_source_ids list; any answer from an acceptable page that is grounded is fine, abstention is fine, an answer from an unacceptable page is a wrong-page answer).
The set is **an evaluation set only**. Nothing is tuned on it; if any analysis changes the pipeline, the set is no longer evidence for that change.

## E - Metrics (`scripts/evaluate_phase12.py`, results in `data/evaluation/phase12_results.json`)

Computed for each configuration separately and per category:
* Router (all questions with a gold card; ambiguous = best rank among acceptable cards): R@1, R@3, R@5, MRR; also on answerable only.
* Page retrieval (answerable questions, oracle page): chunk R@1/3/5/MRR (evidence-bearing chunk); end-to-end "evidence in the context given to the generator" under real routing.
* Answer quality (real routing = product behaviour; oracle routing = generator in isolation): answerable answered-correct / answered-incorrect / abstained; unsupported (absent_detail, not_ingested, unresolved_identity, out_of_domain) correctly abstained / incorrectly answered; absent-detail abstention; grounding failures; citation-evidence failures (answered but the cited chunk of the gold page does not hold the gold evidence); phantom citations (cited chunk not in the context); URL changes (cited URL differs from the stored page URL); wrong-page answers (answered from a page other than the gold / acceptable page); wrong-topic answers (answered where the right outcome is not an answer); support-chain failures.
* Latency per stage (route / retrieve / generate / total): median, p95.
Configurations: `baseline` = Phase 8-10 extractive generator; `evidence` = shipped Phase 11.1 configuration (`rag_evidence`, tau 0.5, no widening); `ollama_raw` = real LLM without the evidence guard; `ollama` = real LLM + `EvidenceGuard` (the shipped Ollama configuration). A higher answer count is never reported as "better": every table pairs answered counts with unsupported-answered and citation-evidence-failure counts.

## F - Real UI E2E (`web/e2e/phase12_browser_e2e.cjs`)

Real Chromium against real servers; no mocked backend for the primary run. Scenarios: normal answer; citation display/click target; abstention; out-of-domain; page_not_ingested; unresolved identity; backend failure (a real server process is stopped mid-session); generator failure (a real server started with `--generator ollama`, which really fails here because Ollama is absent - this is a failure-path test, **not** an LLM evaluation); long answer; markdown/list rendering; code/numeric answer; mobile layout; conversation continuity (history survives reload; second question in the same conversation). Each answer text is compared with the API response for the same question.

## G - Router: reproduce, classify, do not fix blindly

`scripts/phase12_failure_audit.py` reproduces every router miss (gold card not top-1) on the Phase 12 set and on the older sets (Phase 8, 9, 10 DEV/TEST, 11.1 holdouts, the 16 E2E) and classifies it with these **pre-declared, deterministic rules (first match wins)**:
1. `gold_page_not_available` flag is added separately (gold card not ingested) - it does not replace the cause.
2. `identity_hub` - the top-1 card is `conflicting_identity` or `card_identity_only` (a card that can never answer).
3. `sibling_ambiguity` - top-1 and gold share the card `category` (same family) and the gold is within the top 3.
4. `vocabulary_mismatch` - the query shares no stemmed content term with the gold card's title+text.
5. `query_underspecified` - fewer than 3 content terms, or an `ambiguous`-category question.
6. `near_tie_embedding` - the gold is within 0.05 cosine of the top-1 (margin evidence of embedding limitation) and none of the above.
7. `other_ranking` - everything else.
`ood_gate` is reported separately for answerable questions whose router top-1 is right but the status is out_of_domain / no_relevant_page.
**Candidate router changes (not evaluated in this phase)** - listed for a later phase with their adoption rules so that nothing is adopted because "one set improved": (a) card-text query expansion with the 7C titles; (b) dense + lexical rank fusion; (c) sibling-aware re-ranking using page evidence (Phase 10 R). Any of them needs: frozen DEV/TEST sets written before the candidate, router R@1 non-inferior at the 95 % level on TEST, wrong-topic answers not higher, 0 grounding/phantom/chain failures, unresolved-identity top-1 not worse, Phase 4/5/7/8/9 baselines identical, trade-offs reported. **If none passes, the baseline stays.** In this phase none is run because the real-corpus and real-LLM paths cannot be exercised here (see C1/C2).
